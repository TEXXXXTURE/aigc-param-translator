# tools/verifier.md — 出图校验与案例沉淀（进化回路）

> 翻译器不是一次性的：出图结果必须回流，沉淀案例，更新预设库与参数语义库。
> 同时承接分支 B 操作日志 → 指引库 → 反哺分支 C 指引质量。

## 第 1 步 · 出图校验

对照方案逐项判定：

| 维度 | 判定 | 依据 |
|---|---|---|
| 需求匹配 | 是否满足用户需求（主体/风格/比例/数量/一致性） | 需求原文 + 预期（explain.expect） |
| 参数合规 | 实际生效值是否越界、是否踩了已知坑 | params + 语义库"常见坑" |
| 预期对照 | 每个改动项的"预期效果"是否达成 | explain.expect |
| 异常归因 | 不达标时，能否定位到具体参数 | 参数语义 + 操作日志（B 分支） |

结果分级：
- **达标** → 沉淀成功案例。
- **不达标但可定位** → 沉淀失败案例（带归因）。
- **不达标且无法定位** → 标"需人工排查"，不强行归因（禁止编造原因）。

## 第 2 步 · 案例沉淀

条目格式（建议存 `cases/` 或用户资产库）：

```json
{
  "case_id": "string",
  "requirement": "需求原文",
  "plan": "方案摘要（参数 + 理由）",
  "result": "达标 / 不达标",
  "images": ["出图路径/URL"],
  "attribution": "归因：哪个参数/资产/环节导致成败",
  "delta": "改了什么（调参/换资产/换预设）",
  "next_plan": "更新后的建议方案"
}
```

## 第 3 步 · 回流更新（三类）

1. **更新参数语义库**（knowledge/params.md）：
   - 失败案例的归因补进对应参数"常见坑"；
   - 成功案例的稳定做法提炼进"调优方向"。
2. **更新预设库**（routes/presets/）：
   - 同一类需求反复出现且档位稳定 → 新增/微调预设卡；
   - 预设档位被证伪（如"赛博朋克 CFG 8 总过曝"）→ 修正默认档。
3. **更新指引库**（反哺分支 C）：
   - 分支 B 的操作日志（步骤 + 截图 + 结果）转为指引条目；
   - 分支 C 用户反馈"预期不符"的步骤 → 修正该步骤的"预期看到什么"。

## 第 4 步 · 质量闸口

- **禁止**：无归因硬套原因；把单次随机失败当结论；跨平台混用案例（即梦的坑不能直接写进 ComfyUI 的卡，除非语义层确认）。
- **样本要求**：预设档位修正至少 2 个同向案例支撑；单案例只进"待观察"。

## 校验清单

- [ ] 每个案例是否有归因（或显式标"需人工排查"）
- [ ] 回流是否落到三类产物（语义库/预设库/指引库）
- [ ] 预设修正是否有 ≥2 同向案例支撑
- [ ] 是否避免跨平台混用归因
